# AGENTS.md

Next.js 14 (App Router) + Supabase + Gemini: intake on `/upload` is file upload (audio/video/**transcript/**document/image/text**) or a pasted link/YouTube URL → LinkedIn post, newsletter section, short-form script, thread, or carousel — plus an agentic layer (`/agent`) that plans content angles from a transcript, human-gates them, then generates and evaluates drafts. Two roadmaps: `docs/ROADMAP.md` (core app) + `docs/AGENTIC_ROADMAP.md` (agent). Newer subsystems live behind `docs/ARCHITECTURE_FREEZE.md` (locked contracts), `docs/IMPLEMENTATION_MAP.md`, `docs/data-model.md`. `docs/API.md` is the authoritative HTTP-surface reference (kept current — update it when adding/renaming routes).

> This file and the README are kept current; when they disagree, trust the code + migrations. Every user-owned table (base + `V4_` + `content_intelligence`) uses the per-user RLS grammar (`auth.uid() = user_id`) — EXCEPT the ledger/contract tables (`events`, `usage_events`, `subscriptions`, `subscription_events`, `profiles`), which are service-role-write with **no client policies**. `docs/data-model.md` is the table-level authority; `docs/IMPLEMENTATION_MAP.md` (current ground truth — `docs/agentic-v2-audit.md` is stale) + `docs/ARCHITECTURE_FREEZE.md` (locked runtime contracts) must be read before touching registry/RLS/service-role/timing code.

## Supabase clients (do not mix these up)
- `lib/supabase/client.ts` — browser client (client components only).
- `lib/supabase/server.ts` — `createClient()` = user-session client (cookies, RLS). `createServiceClient()` = service-role, **bypasses RLS**, created via `require("@supabase/supabase-js")` with `persistSession: false`. Allowed in API routes / server components for privileged writes (`outputs` has no update/delete RLS policy — use the service client). Never import it into client-facing components.
- SSR auth cookie is stored as **raw JSON**, not base64url (only the chunked >3180-char path and optional `cookieEncoding: "base64url"` differ). Relevant if you hand-build test cookies.

## Auth
Email/password via Supabase Auth: `app/login/page.tsx` (sign-in / create account / forgot password), `/api/auth/callback` does the PKCE exchange and only allowlists `?next=reset-password`, `app/reset-password/page.tsx` calls `updateUser({password})` then signs out. Plus "Sign in with Google" via the app's own Google OAuth client (`lib/google/auth.ts`): `/api/auth/google/connect` → Google consent (state+nonce bound to a `google_auth_state` httpOnly cookie) → `/api/auth/google/callback` exchanges the code for an id_token and calls `supabase.auth.signInWithIdToken({ provider: "google", token, nonce })` which auto-creates the user and sets the session cookie; no provider redirect-URI registration needed beyond the Google console entry. `middleware.ts` protects `/dashboard`, `/upload`, `/repurpose`, `/branding`, `/connections`, `/library`, `/agent`, `/publish`, `/content`, `/settings`, `/reset-password` (plus the account delete/export APIs) — add new authed routes there.

## Types gotcha (important)
`types/supabase.ts` is a **handwritten placeholder**, not generated (the `supabase` CLI is not authenticated → `npm run db:types` fails; it needs `SUPABASE_ACCESS_TOKEN`). When you change `supabase/schema.sql` **or** `supabase/schema_agentic.sql`, update it by hand. Keep every table's `Row`/`Insert`/`Update`/`Relationships: []` plus top-level `Views: Record<string, never>` and `Functions: Record<string, never>`; dropping those breaks `.insert().select().single()` typing with a confusing `never[]`. (Currently: `sources`, `outputs`, `jobs`, `transcripts`, `user_prompts`, `youtube_connections`, `buffer_connections`, `drive_connections`, `content_intelligence`, and all six `v4_*` tables.)

## Database & schema
- Migrations: `supabase/migrations/20260907*.sql` (0001 baseline → 0007 `buffer_connections`) + `20260908000001` (Paddle) → `20260908000004` (`content_intelligence`) → `20260910000001` (Buffer MCP `api_key` + distribution `metrics`) are the **reproducible path** — a fresh `supabase db push` converges to the full schema; `data-model.md` calls `supabase/migrations/` the source of truth and `supabase/schema.sql` "retained only as reference." `supabase/schema_agentic.sql` is the apply-by-hand export for the `V4_` tables only (`verify-agentic` checks against it) — it does NOT contain `buffer_connections`, `content_intelligence`, or the ledger tables. All migration statements are idempotent (`if not exists` guards) so re-running on the already-migrated live DB is a no-op.
- Code must degrade gracefully when columns/tables are missing. Established pattern — match the PostgREST error (`/could not find the\s*\w*\s*["']?\w+|does\s*not\s*exist|PGRST205|42P01/`) and retry without the column, or return `{}`/defaults. See `lib/prompts.ts` (`getUserPrompts` returns `{}` when `user_prompts` is absent) and the `formats`/`updated_at` fallbacks in `app/api/process/route.ts` + `app/api/outputs/[id]/regenerate/route.ts`.
- Tables: `sources` (file, YouTube, transcript, **or URL/paste-a-link**, RLS per-user, `source_type` audio|video|youtube|transcript), `transcripts` (one canonical ingested transcript per source — `provider`, `language`, `duration_seconds`, `content`; worker upserts on `source_id` after `ingestSource`, so this is the durable source of truth while `sources.transcript` stays denormalised), `outputs` (one row per format), `jobs` (async queue, has `formats[]`), `user_prompts` (PK `user_id,format`; `brand_voice` + per-format overrides; blank = built-in default), `youtube_connections` (one per user; `refresh_token`/`access_token` AES-GCM encrypted at rest with `YOUTUBE_TOKEN_ENCRYPTION_KEY`), `content_intelligence` (grounded topics/themes/claims/quotes for the recommendations engine, per-user RLS), plus the agentic `V4_` set (see table below). Private `sources` storage bucket: uploads go to `{user_id}/{filename}`, YouTube extracts to `{user_id}/youtube/{ts}-{name}.mp3`. Ledger/contract tables (`events`, `usage_events`, `subscriptions`, `subscription_events`, `profiles`) are **service-role-write with no client policies** — not part of the per-user RLS grammar. `20260908000002`/`0003` loosen `sources` constraints for file-kind + paste-a-link URL intake (Phase 1).
- Agentic `V4_` tables (schema_agentic.sql, all RLS per-user, cascade from `auth.users`): `v4_agent_runs` (durable run — status `created|planning|awaiting_approval|executing|evaluating|done|failed|cancelled` + `plan`/`transcript_snapshot`/`cost_units`/`output_ids`), `v4_agent_steps` (append-only timeline, `kind` check-constrained to planning|source|generation|review|distribution|strategy), `v4_content_ideas` (planner angles + per-angle `approved` + `evaluation`), `v4_agent_preferences` (brand voice + `edit_signals`; `unique(user_id)`), `v4_distribution_jobs` (queue: draft|scheduled|published|failed|cancelled + `external_id`/`scheduled_at`/`error_message`), `v4_content_strategies` (`unique(user_id, title)`, `source` check).
- `buffer_connections` (migration 0007 + `20260910000001`) — one row per user, Buffer OAuth tokens **AES-GCM encrypted** at rest with `BUFFER_TOKEN_ENCRYPTION_KEY` + `access_token_expires_at`, `buffer_account_id`, `buffer_username`, plus an encrypted `api_key` column (MCP connector credential; see Stage 4b). Written only by the OAuth callback / refresh flow in `lib/buffer/` and the API-key management in `components/connections-buffer.tsx`; never construct rows by hand.
- `drive_connections` (migration `20260908000005`) — one row per user, Google Drive OAuth tokens **AES-GCM encrypted** at rest (same key material as YouTube via `lib/crypto.ts`) + `access_token_expires_at`, `drive_email`, `drive_name`. Same pattern as `youtube_connections`; routes under `app/api/integrations/drive/`, reuses the Google OAuth client (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`) with the Drive scope. Written only by the OAuth callback / refresh flow in `lib/drive/`; never construct rows by hand.

## Pipeline (enqueue → worker → live dashboard)
- `POST /api/repurpose` is **enqueue-only** → returns `{ jobId }`. Accepts sources in `uploaded` **or** `failed` state (the dashboard's "Try again" re-queues a failed run). Two gates: a rolling-minute rate limit (`lib/rate-limit.ts`, counts `jobs` rows — keep the `jobs_user_created_idx` index) **and** an atomic monthly-cap + idempotency check via the `enqueue_job` RPC (`20260907000004_billing_ledger.sql`): one transaction per user (advisory lock) does "used < limit" → insert → `reserve` ledger write, and replays a client idempotency key. If the RPC fails (migration missing) the route returns **503 fail-closed** — never falls back to an unchecked insert. Limits come from `lib/billing/plans.ts` server-side.
- `POST /api/process` is the worker: claims a job atomically (`queued`→`running`; `running` jobs re-claimable after 10 min stale window), ingests via `ingestSource` (AssemblyAI transcription only for audio/video/YouTube sources — transcript sources skip transcription entirely), persists the canonical transcript via `saveTranscript` (`lib/ingestion/save.ts`, upsert on `source_id`; missing table degrades to a log + `sources.transcript` only), runs the selected formats in parallel, writes `outputs`, flips `sources.status`. Regeneration deletes prior outputs first. Kept as a single Vercel/serverless invocation — long transcripts may time out (the claim window makes the job resumable).
- `app/dashboard/source-list.tsx` subscribes to Realtime `postgres_changes` (optional, added via `alter publication supabase_realtime` blocks in schema.sql) **and** polls `/api/sources` every 4s, re-kicking `/api/process` for queued jobs. Duplicate kicks are harmless (atomic claim). Failed sources get a "Try again" button; an `uploaded` source whose enqueue was lost gets "Start processing" — both `POST /api/repurpose` then kick the worker. When SSE emits an `error` event the list refetches so the failed status + message appear on the card.

## Agentic system (`/agent`)
Plans content angles from a source's transcript, human-gates them, then generates + deterministically evaluates drafts. Design choices that must survive refactors:
- **Flow**: `POST /api/agent/runs` (create, requires source `done`/`failed`) → `POST /api/agent/process` (SSE worker) → `runPlanning` (single Gemini call, **not** a swarm) → parks run at `awaiting_approval` with angles in `v4_content_ideas` → `POST /api/agent/runs/[id]/approve` (per-angle toggles; reject-all → `cancelled`) → `runExecution` generates one draft per approved angle × suggested format and writes them straight into the **existing `outputs` table** — agent drafts appear in `/library` + the `/repurpose/[id]` editor, no new viewer code.
- **Deterministic, bounded**: `lib/agent/evaluator.ts` scores drafts with a weighted rubric (length / format-shape / grounding) — **no LLM judge call**. Script/planner prompts live in `lib/ai/generate.ts` + `lib/agent/planner.ts`; planner uses `gemini-3.6-flash`.
- **Autonomy is static**: `lib/agent/permissions.ts` fixes capabilities per mode (`assist`|`execute`|`automate`) once: `assist` never revises, `execute` allows one bounded revision on a flagged draft, `automate` additionally enables `distribute` + `strategize`. Tools declare required modes in `lib/agent/tools/registry.ts`; the orchestrator filters by the run's mode before anything runs. The distribution/strategy **mode gating is about the agent driving pre-approval sends** — a human-initiated send from the publish queue is a separate, always-real path (below).
- **Claim/resume mirrors the worker**: `lib/agent/orchestrator.ts` claims runs atomically with a 10-min stale window (same semantics as `/api/process`); the **service client** does claims/writes (mirrors `outputs`-write pattern), the **user client** does ownership checks in each route. `v4_agent_steps` is the durable audit timeline — the UI re-reads the DB on short polling instead of trusting the SSE stream.
- UI: `app/agent/page.tsx` + `components/agent/*` (`agent-workspace`, `run-list`, `plan-view`, `run-detail`, `timeline`). Durable state means new screens should poll `/api/agent/runs/[id]`, not hold memory. Agent domain types: `types/agent.ts` (mode/run/step/idea types + `AGENT_MODE_LABEL`); `lib/status.ts` adds `AGENT_STATUS_LABEL`/`AGENT_STATUS_STYLE`.

## Stage 4 — Buffer distribution
The schedule/publish path is **real** (bring your own Buffer account), not a stub. Key files: `lib/buffer/` (`oauth.ts` authorize/exchange/refresh, `connections.ts` encrypted-at-rest persistence + `getFreshAccessToken`, `crypto.ts` AES-256-GCM, `client.ts` parseErrorDetail + createUpdate), `lib/agent/tools/distribution.ts`, `components/agent/publish-queue-panel.tsx`.
- **Flow**: `/connections` Buffer connect (CSRF state cookie, constant-time check) → callback persists encrypted tokens + `access_token_expires_at` into `buffer_connections` → queue panel (`app/api/agent/queue/*`) lists jobs; a human clicks "Send now"/"Schedule" with a target profile → `lib/agent/tools/distribution.ts` → `getFreshAccessToken(userId)` (refreshes via `refresh_token` grant when within 60s of expiry; stale token if no refresh_token; refresh failure throws → job `failed`) → fetch profiles → pick profile by `profileIds` (explicit; unmatched → honest failure, no silent fallback) → `POST api.bufferapp.com/1/updates/create.json` with `scheduled_at` when scheduling.
- **Manual approval only**: the send is wired to a human click (and `automate`-mode agent sends through the tool registry). Never auto-publish. Immediate send → job `published` (external_id + published_at); future send → job stays `scheduled` with `external_id` + `scheduled_at` set — **never fabricate a `published` state** for a post Buffer hasn't aired. Ratelimited with Retry-After surfaced ("Retry after Xs."), no retry loop.
- Auth gate on queried sends: `publishingChannelsConnected` / `getFreshAccessToken` returning null → 503 `PUBLISH_NOT_CONNECTED`. Tests live in `lib/buffer/connections.test.ts` + `lib/agent/tools/distribution.test.ts` (mock `getFreshAccessToken` returning `{ token, refreshed }` or `null`, and `global fetch`), covering refresh/expiry/rotation, explicit profile selection, unmatched-profile rejection, and scheduled-vs-immediate job state.

### Stage 4b — MCP connector (agent scheduling, repurpose, metrics)
The agent's new capabilities run over Buffer's MCP connector (`https://mcp.buffer.com/mcp`), authenticated by a **per-user Buffer API key** (`publish.buffer.com/settings/api`) stored **AES-256-GCM encrypted** in `buffer_connections.api_key` (migration `20260910000001`, same `BUFFER_TOKEN_ENCRYPTION_KEY`; `getApiKey` degrades to null if the column is absent **or the ciphertext is unreadable**). Saving a key (`saveApiKey`) reads the row **without decrypting** (`getRawConnection`) and preserves existing ciphertext verbatim — an undecryptable legacy row (encryption key rotated/mismatched between deploys) must never block re-saving, and a bad row is overwritten on the next save. Api-key-only rows use sentinels (`buffer_account_id='api-key'`, `buffer_username='Buffer API key'`, `access_token=''`) — `connectionHasOAuth()`/`getFreshAccessToken()`/`publishingChannelsConnected` (which now filters `.neq("access_token","")`) treat them as **not** connected, so manual GraphQL "Send now" stays OAuth-gated. Key files: `lib/buffer/mcp.ts` (stateless streamable-HTTP JSON-RPC: initialize → initialized → tools/call, echo `Mcp-Session-Id`, Bearer auth, `structuredContent`-first parsing, `BufferMcpError` with `rate_limited`/`retryAfterMs`), `lib/agent/schedule.ts`.
- **Capabilities**: only `automate` mode — `scheduleRunOutputs` (create_post `addToQueue`; no API key → `skipped` step + run stays `done`; `newsletter`/empty draft/unknown channel per-output skipped; failed create → `failed` job + step, never aborts the run), `refreshRunMetrics` (paginated `list_posts includeMetrics`, capped 4×100, → `metrics` jsonb + `metrics_refreshed_at` on `v4_distribution_jobs`), `GET /api/agent/posts` (repurpose picker), `POST /api/agent/repurpose` (MCP `get_post` → transcript-style `sources` row with marker `storage_path` status `done` + `saveTranscript` + a new `v4_agent_runs`). Format→platform map: `linkedin_post→linkedin`, `shortform_script→x`, `thread→x`, `carousel→linkedin`, `newsletter→none`. UI: `components/agent/buffer-post-picker.tsx` (shared), repurpose cards in `run-detail` + `publish-queue-panel` (`/agent?run=` deep link), `components/connections-buffer.tsx` API-key management, Performance panel (`run-detail`) fed by `refreshRunMetrics`. Migration `20260910000001` also adds those `metrics` columns; remember `types/supabase.ts` (update by hand) before `verify:agentic` regressions.

## Stage 5 — Paddle Billing (paid tiers)
Checkout + webhook scaffold lives in `lib/billing/paddle.ts` (pure helpers + `applyPaddleEvent`), `/api/billing/checkout` (POST, authed, creates a transaction → `{ url }`) and `/api/billing/webhook` (signature-verified, idempotent). It is **inert until the env vars exist**: `getPaddleConfig()` returns null without `PADDLE_API_KEY` + `PADDLE_WEBHOOK_SECRET`, so checkout answers 503 and webhook 401 — the app runs unchanged. Migration `20260908000001_paddle_billing.sql` adds `'paused'` to `subscriptions.status` and `subscription_events.paddle_event_id` (unique, null-excluded) so duplicate webhook deliveries are a no-op; app code degrades if that migration hasn't been applied.
- **Model**: `profiles.plan` is the ENFORCEMENT source of truth (read by `resolvePlan` in `lib/billing/entitlements.ts`). `subscriptions` (migration 0004) is the provider-contract row. `applyPaddleEvent` writes BOTH via the service client: activation sets `profiles.plan` + `plan_status='active'`; `subscription.canceled` downgrades to `plan='beta'`/`plan_status='cancelled'` (real downgrade now — no cancel-at-period-end defer yet, flagged); `past_due`/`paused` keep the plan but flag `plan_status='cancelled'`.
- **Env**: `PADDLE_API_KEY`, `PADDLE_WEBHOOK_SECRET` (sandbox login), `PADDLE_ENV` (`sandbox|production`, default production), `PADDLE_PRICE_ID_CREATOR/PRO/STUDIO` (unset = that plan not purchasable), `PADDLE_API_VERSION` (default `1`). Signature scheme: `Paddle-Signature: ts=<unix>;h1=<hex>`, HMAC-SHA256 over `${ts}:${rawBody}` keyed by the notification-destination secret; raw body via `request.text()`, 5s replay window (tests override `now`).
- **Owner TODOs to go live**: create seller/business sandbox → product + recurring `pri_` prices per plan → notification destination for `POST https://<origin>/api/billing/webhook` (grab the signing secret) → set env on Vercel → apply migration 0008 → flip `PADDLE_ENV=production` with live catalog + webhook secret. `paused`/grace-period, cancel-at-period-end, Paddle customer pre-creation, and spend/error-rate alerting on `subscription_events` remain open decisions. Tests: `lib/billing/paddle.test.ts`.

## Logging
`lib/logger.ts` (server-only, zero deps) emits one JSON line per event via `log.info` / `log.warn` / `log.error`. Wired into AssemblyAI submit/poll, Gemini/OpenRouter generation, and job claim/completion/failure in `/api/process`, `/api/repurpose`, `/api/outputs/[id]/regenerate`. Fields are ids/durations/formats — never transcripts, emails, or other PII. If `LOG_WEBHOOK_URL` is set, lines are fire-and-forget POSTed there too (a broken webhook never breaks the app). `LOG_LEVEL` gates verbosity (`info` default, `warn` to quiet success paths).

## YouTube ingestion
Two mechanisms behind the same seam (`lib/ingestion/youtube.ts`), both producing the canonical `TranscriptDocument`:
- **OAuth captions** (preferred, needs a `youtube_connections` row): connected user's own video captions pulled via the YouTube Data API (`lib/youtube/client.ts`) — a caption track list → best track (human-uploaded over ASR) → SRT download → parse (`lib/captions.ts`) → transcript. No mp3 download, no AssemblyAI, no yt-dlp. Any failure falls back to legacy (so a job never dies just because captions are unavailable).
- **Legacy yt-dlp** (archived at `lib/ingestion/providers/ytdlp.ts`): validate URL → download bestaudio → extract mp3 → upload to storage → AssemblyAI. Probe via `fetchVideoInfo` (availability + duration vs `MAX_INPUT_SECONDS`) before download; `describeYoutubeError` maps failures to friendly messages. No cookie/cookie-file support and no dedicated API routes — this path is kept only as a fallback for public videos without captions.

## Transcript ingestion
`lib/ingestion/transcript.ts` turns an uploaded transcript file into a `TranscriptDocument` with no transcription cost: `.srt`/`.vtt` subtitle cues (with timestamps) or plain `.txt` text. Subtitle parsing lives in the shared pure module `lib/captions.ts` (`parseSrt`, `parseVtt`, `looksLikeSubtitles`, `segmentsToText`) — also used by the YouTube OAuth path. Follows the same `source_type` + `storage_path` convention (`'transcript'`), gated by `TRANSCRIPT_FILE_EXTENSIONS` in `lib/limits.ts`.

OAuth plumbing: `lib/youtube/oauth.ts` (authorize/exchange/refresh, server-only; scopes `youtube.readonly`+`youtube.force-ssl`, `access_type=offline`+`prompt=consent` for a guaranteed refresh token), `lib/youtube/connections.ts` (encrypted-at-rest persistence + token refresh/caching). Routes: `/api/integrations/youtube/connect` (→ Google consent, CSRF state cookie), `/callback` (exchange + persist, constant-time state check), `/status` (channel name only), `/videos` (the user's uploads for a picker), `/disconnect`. The refresh token never leaves the server, and the browser only ever gets the authorize URL.

URL parsing is via the pure `lib/youtube-url.ts` (also used client-side on `/upload`). The cookie-sync extension and its `/api/youtube/*` routes were retired (Commit 5); `cookies.txt` remains gitignored for safety. Set `YTDLP_JS_RUNTIME` (e.g. `node`) if yt-dlp needs a JS runtime. Size/duration/daily-rate caps live in `lib/limits.ts`.

## Legal & deployment
- `/legal/terms` + `/legal/privacy` are plain-English policy pages (server components via `components/legal-doc.tsx`), linked from the login page and the app-shell sidebar footer. Written as plain language, NOT legal advice; each page defines `CONTACT` — a placeholder email that must be swapped for a real address before launch. Automated transcript/content scanning is deliberately deferred (see ROADMAP Phase 2).
- Vercel: project `vervai` on team `fragile-frogs`, aliased to `verv-ai.vercel.app`; deploy with `vercel link --scope fragile-frogs` then `vercel deploy --prod`. Runtime keys are set as encrypted env vars on Vercel — `.env.local` remains the local source of truth (nothing Vercel-specific is checked in; `.vercel` is gitignored). Caveat: Vercel's serverless runtime has no yt-dlp/ffmpeg binaries, so the YouTube URL path only works on a host that provides them — the file-upload and transcript paths work anywhere.
- Uptime probes are public and no-op-safe: `GET /api/healtz` → always `200` liveness (used e.g. at `https://vervai.onrender.com/api/healtz`); `GET /api/healthz` → `200`/`503` liveness + Supabase reachability (3s timeout). `GET /api/integrations/debug` (authed) prints exact OAuth redirect URIs + config presence.

## UI conventions
- Design-system classes defined in `app/globals.css`: `.form-label`, `.form-control`, `.btn-*` (`btn-primary`, `btn-sm`, `btn-text-primary`, ...), `.side-nav-link(.active)`, `.badge`, `.caption`. Reuse these rather than inventing new button/input styles.
- Tailwind: `primary` ramp (`primary-500 = #3923c7`, in `tailwind.config.ts`) + `theme-*` tokens. Path alias `@/*` → repo root.
- App chrome is `components/app-shell.tsx` (`NAV_ITEMS` sidebar + mobile drawer) — new nav items go there. `components/logo.tsx` renders `/icon.png` via `next/image`; `app/icon.png`/`apple-icon.png`/`favicon.ico` are picked up automatically by Next — the SVG-in-logo era is over.
